# Авито.Кухня: план разработки MVP

> План, по которому реализуется проект. Приложен к решению согласно разделу
> «Использование ИИ» задания.

---

## 1. Контекст и цель

Требуется MVP бэкенда сервиса доставки еды: закрытый список заведений принимает
заказы пользователей через нашу площадку. Оценивается **подход к проектированию**,
а не production-готовность — упрощения допустимы, но должны быть осознанными и
описанными.

Из критериев приёмки следует состав репозитория:

- запуск целиком через `docker compose up`;
- CJM пользователя **и** заведения в code-generated диаграммах (PlantUML);
- миграции со схемами БД + OpenAPI спецификации;
- README: описание проекта, C4 (Level 2/3), схема БД;
- конфиг линтера в репозитории;
- отдельный сервис-пример заведения, поднимаемый вместе с основным приложением.

**Центральное архитектурное решение:** брокер сообщений (Kafka) как асинхронный
транспорт между площадкой и заведениями. Это даёт изоляцию отказов (заказ
принимается, даже когда касса заведения недоступна) и масштабирование по
партициям после MVP.

| Язык | Go 1.26+ | Требование задания |

## 3. Архитектура

### 3.1 Схема взаимодействия

```
                    ┌──────────────────────────────────────────┐
   браузер          │            kitchen-api  (:8081)          │
   клиента          │                                          │
      │             │                                          │
      │ ① REST      │   ┌────────────┐      ┌──────────────┐   │
      ├────────────►│   │ HTTP слой  │─────►│  Postgres    │   │
      │             │   └────────────┘      │  kitchen     │   │
      │ ⑥ SSE       │   ┌────────────┐      │  + outbox    │   │
      │◄────────────┤   │  SSE hub   │      └──────┬───────┘   │
                    │   └─────▲──────┘             │           │
                    │         │              ┌─────▼────────┐  │
                    │         │              │    worker    │  │
                    └─────────┼──────────────┴─────┬────────┴──┘
                              │ ⑤                  │ ③
                    ┌─────────┴────────────────────▼──────────┐
                    │              Redpanda (Kafka)           │
                    │  kitchen.orders.v1       key = venue_id │
                    │  kitchen.order-status.v1 key = order_id │
                    └───────────────────┬─────────────────────┘
                                        │ ④ consume
                    ┌───────────────────▼─────────────────────┐
                    │            venue-service                │
                    │   своя БД (dishes, incoming_orders)     │
                    │   автопилот: статусы по таймерам        │
                    └───────────────────┬─────────────────────┘
                                        │ ⑦ REST partner API (X-Api-Key)
                                        └──────────► kitchen-api
```

Три канала между сервисами, у каждого своя роль:

| Канал | Направление | Что несёт | Почему так |
|---|---|---|---|
| Kafka `kitchen.orders.v1` | площадка → заведения | `order.created`, `order.cancelled` | **Событие.** Заведений много, они могут лежать |
| REST `/api/v1/partner/*` | заведение → площадка | статусы, меню, стоп-листы, смена | **Команда.** Нужен ответ `409` при невалидном переходе |
| Kafka `kitchen.order-status.v1` | площадка → площадка | `order.status_changed` | Шина фан-аута для SSE: публикует `worker`, потребляет `kitchen-api` |

**Принцип:** async там, где решается задача доставки; sync там, где нужна
валидация и немедленный ответ.

### 3.2 Жизненный цикл заказа

1. `POST /api/v1/orders` → `kitchen-api`.
2. **Одна транзакция:** резерв остатков + `orders` + `order_items` со снапшотом
   цен + `order_status_history` + строка в `outbox_messages`. COMMIT → `201`.
   **Kafka нет в горячем пути:** брокер лежит — заказ всё равно создан.
3. Джоба `outbox` в `cmd/worker` читает
   `WHERE published_at IS NULL ... FOR UPDATE SKIP LOCKED`, публикует,
   проставляет `published_at` (§3.5).
4. `venue-service` (группа `venue-<uuid>`) получает событие → дедуп по `event_id`
   → пишет в свою БД → коммитит offset. Заказ принят в работу заведением.
5. Клиент держит открытым `GET /orders/{id}/events`.
6. Заведение принимает заказ → `POST /partner/orders/{id}/accept`.
7. `SELECT ... FOR UPDATE` → проверка владельца по API-ключу → проверка FSM →
   `UPDATE` + история + outbox в статус-топик. COMMIT → `200`.
8. `worker` — **отдельный процесс** — публикует `order.status_changed`.
9. `kitchen-api` консьюмит статус-топик (уникальный `group.id` на инстанс →
   broadcast), находит подписчика в своём хабе и пишет в сокет.

Задержка end-to-end ≈ 300 мс в худшем случае, из них основное — интервал
поллинга outbox `OUTBOX_POLL_MAX` (§3.5). Для человека, смотрящего на статус
заказа, незаметно.

**Заказ, остановленный не заведением** (отмена клиентом, авто-отказ
`order-reaper` §4.1): транзакция с возвратом остатков → **два** outbox-события.
Это не дубль, а fan-out: строка outbox несёт ровно один топик и один ключ, а
адресата два. `order.cancelled` идёт в топик заказов с ключом `venue_id` — в ту
же партицию, что и `order.created`, иначе касса могла бы увидеть отмену раньше
самого заказа. `order.status_changed` идёт в статус-топик с ключом `order_id` —
там гарантируется порядок статусов одного заказа. Заведение, отклонившее заказ
своей ручкой, второго события не получает: результат оно узнало из синхронного
`200`.

### 3.3 SSE и хаб подписчиков

Хаб подписчиков — `map[orderID]map[*subscriber]struct{}` с мьютексом **внутри
процесса**. Статус меняет не тот процесс, что держит соединение клиента: REST
от ресторана принимает `kitchen-api`, публикует событие `worker`, а SSE-поток
живёт в памяти `kitchen-api`. Поэтому между ними и стоит топик, а не вызов
функции.

**Маршрутизация не вычисляется.** Событие получает каждый инстанс `kitchen-api`;
инстанс смотрит в свою мапу по `order_id`; нашёлся подписчик — пишет, не нашёлся
— no-op. Никакого реестра «где сидит клиент» — состояния, которое можно
рассинхронизировать, просто нет. В MVP инстанс один, но именно поэтому его
можно будет добавить вторым, ничего не переписывая.

Consumer group в Kafka = «команда», сообщение получает один участник каждой команды:

- `kitchen.orders.v1`, группа `venue-<uuid>` — **очередь**: заказ готовят один раз;
- `kitchen.order-status.v1`, группа `sse-<hostname>` — **broadcast**: каждый
  инстанс сам себе команда, поэтому событие получают все.

Требования к реализации хаба:

- подписка **до** чтения снапшота из БД, затем отбрасывание событий с
  `seq <= snapshot_seq` (иначе теряется статус, сменившийся между `SELECT` и
  `Subscribe`);
- буферизованный канал (16). Если буфер полон — подписчик отстал (уснувший
  ноутбук: сокет жив, байты не читаются). Блокирующая запись повесила бы горутину
  консьюмера под `RLock`, а через неё и весь процесс. Тихо ронять событие тоже
  нельзя, поэтому **закрываем такому подписчику поток**: браузер переподключится
  через ~3 с с `Last-Event-ID` и доберёт пропущенное из `order_status_history`.
  Ничего не теряется — переиспользуем механизм реплея, нужный и так для обрывов
  сети;
- закрыть соединение **из `Publish` нельзя**: `http.ResponseWriter` принадлежит
  горутине своего хендлера, а `Unsubscribe` требует `Lock()` поверх уже взятого
  `RLock` (`RWMutex` не апгрейдится → дедлок). Поэтому у подписчика есть канал
  `done`: `Publish` делает `once.Do(func(){ close(s.done) })`, хендлер видит его
  в `select` и выходит сам, а `defer Unsubscribe` уже безопасно берёт запись.
  `sync.Once` — потому что до пробуждения хендлера `Publish` может попасть в эту
  ветку повторно, а второй `close` канала паникует.
  Счётчик `sse_subscriber_lagged_total` живёт в хабе (`atomic.Int64`) и попадает
  в лог на каждое отставание: метрик в MVP нет, а ручка, которую никто не
  скрейпит, — лишний артефакт. Рост счётчика = сигнал, что буфер мал;
- heartbeat-комментарий раз в 15 с, заголовок `X-Accel-Buffering: no`;
- `id:` = `order_status_history.id`; при реконнекте браузер шлёт `Last-Event-ID`,
  доотдаём пропущенное из БД. Кадр `snapshot` идёт **без** `id:` — это состояние
  заказа, а не шаг его истории, и двигать `Last-Event-ID` он не должен; за ним
  идут `status_changed` со своими `id`, поэтому обрыв посреди реплея ничего не
  теряет;
- `Unsubscribe` в `defer` + удаление опустевшей мапы (иначе течёт).

**SSE — best-effort.** Никто не подключён — событие исчезает, и это нормально:
правда в `orders` и `order_status_history`, клиент увидит её обычным
`GET /orders/{id}`.

### 3.4 Почему в compose одна реплика

Масштабирование горизонтальными репликами — не предмет задания, а балансировщик
перед ними стоил бы лишнего контейнера и конфига ради строчки в логе. Поэтому
`kitchen-api` в compose один и слушает `:8081` напрямую.

Асинхронность это не упрощает: `kitchen-api` и `worker` — **разные процессы**,
и статус доезжает до SSE-клиента через Kafka, а не через общую память. Именно
этот шов и делает вторую реплику вопросом одной строки в compose, а не
переписывания кода (§3.3).

### 3.5 Фоновый процесс `cmd/worker`

Один контейнер, несколько независимых джоб-горутин на общем пуле:

| Джоба | Период | Что делает |
|---|---|---|
| `outbox` | адаптивно, 0–250 мс | публикует накопленное в Kafka |
| `order-reaper` | 15 с | автоотказ заказов, не принятых за `ORDER_ACCEPT_TIMEOUT` |
| `courier` | 5 с | закрывает заказы, уехавшие дольше `ORDER_DELIVERY_DURATION` назад |
| `idempotency-gc` | 10 мин | `DELETE FROM idempotency_keys WHERE expires_at < now()` |

Все джобы выбирают строки через `FOR UPDATE SKIP LOCKED`: упавшая посреди батча
или зависшая джоба не держит очередь — следующая итерация просто берёт следующие
свободные строки. Выбора лидера нет и не нужно.

**Порядок публикации.** Нужен он только **в пределах агрегата**: `order.created`
обязан уехать раньше `order.cancelled` того же заказа, статусы одного заказа не
должны переставиться. Порядок между разными заказами не значит ничего.

На записи он уже обеспечен: любой переход начинается с `SELECT ... FOR UPDATE`
по строке `orders`, поэтому две транзакции одного заказа не перекрываются и их
`id` в `outbox_messages` монотонны в доменном порядке. В общем случае `id`
порядку коммитов не соответствует — значение sequence берётся на INSERT, и
длинная транзакция коммитится после короткой, начавшейся позже, — но внутри
агрегата этой гонки нет.

Джоба `outbox` обязана этот порядок не сломать:

- батч забирается `ORDER BY id`, а не `ORDER BY created_at`: `created_at` — это
  `now()`, момент старта транзакции, у обоих событий отмены он одинаковый, и без
  тай-брейкера порядок недетерминирован. Частичный индекс под это построен по
  `id` (§5);
- продюсер синхронный: асинхронная отправка не ждёт подтверждений и порядок
  внутри ключа не держит;
- `published_at` проставляется **после** ack, а не до, иначе потерянное
  сообщение выглядит успешно опубликованным.

Дальше порядок держит сам брокер: одинаковый ключ → одна партиция.

**Воркер в MVP один** (§3.4), и порядок публикации держится именно этим.
`SKIP LOCKED` сам по себе второй экземпляр не разрешает: два события одного
заказа попали бы в батчи разных воркеров, и второй опубликовал бы раньше
первого. Как добавить второй, не сломав порядок, — в §11.

**Публикация — только поллинг, с адаптивным бэкоффом** (`LISTEN/NOTIFY`
сознательно не используем: он всё равно не даёт гарантий — уведомления теряются
при обрыве соединения, — то есть поллинг пришлось бы оставить страховкой, а
за ускорение платить выделенным соединением и несовместимостью с pgbouncer в
transaction pooling):

```
батч полный (100 строк) → сразу следующая итерация, есть завал
батч частичный          → пауза 50 мс
батч пустой             → удвоение до OUTBOX_POLL_MAX (по умолчанию 250 мс)
```

Под нагрузкой цикл не спит, на холостом ходу — 4 запроса в секунду по частичному
индексу `WHERE published_at IS NULL`, что на пустой таблице стоит доли миллисекунды.

`OUTBOX_POLL_MAX` — прямая ручка «задержка против холостой нагрузки», единственная,
которая теперь определяет время доставки события. 250 мс незаметны человеку,
смотрящему на статус заказа, и дёшевы для БД.

## 4. Домен

### 4.1 FSM заказа

```
CREATED ─accept→ ACCEPTED ─start→ COOKING ─ready→ READY ─handover→ DELIVERING ─deliver→ DELIVERED
   │                 │
   ├─reject→ REJECTED   (возврат остатков)
   └─cancel→ CANCELLED  (только из CREATED/ACCEPTED, возврат остатков)
```

Переходы — чистая функция без БД (`internal/domain/order`), легко юнит-тестируется.
Применение — под `SELECT ... FOR UPDATE` + инкремент `version`.

**FSM задаётся данными, а не `switch`** — таблица переходов
`map[{fulfillment, from, event}]Status`. Сегодня в ней только `DELIVERY`, лишней
абстракции нет. Это задел под самовывоз (§11): добавление ветки
`READY --pickup--> PICKED_UP` станет двумя строками в мапе + значение в enum +
`ALTER TABLE orders ADD COLUMN fulfillment_type DEFAULT 'DELIVERY'`, без правки
вызывающего кода. Поэтому же `orders.address` изначально nullable
(обязательность проверяется валидацией заказа, а не схемой).

Автоотказ: заказ не принят за `ORDER_ACCEPT_TIMEOUT` (прод 5 мин, демо 30 с) →
система сама переводит в `REJECTED`, заказ не висит вечно из-за упавшей кассы.
Делает джоба `order-reaper` (§3.5) — **тем же доменным переходом**, что и ручное
отклонение: возврат остатков, история с `actor = 'system'`. Событий два, как и
при отмене клиентом, и по той же причине: остановило заказ не заведение, значит
кассу надо догнать по её каналу (§3.2). Параллельной ветки логики нет, иначе она
разъедется с основной. Гонка «повар принял на 4:59.9» решается `FOR UPDATE`:
проигравший видит статус, из которого переход запрещён, и пропускает заказ.

`DELIVERING → DELIVERED` — единственный переход, который не инициирует ни
заведение, ни клиент: заказ закрывает сама площадка, со стороны доставки. Ручки
`deliver` в партнёрском API поэтому нет и быть не должно — на `handover`
заведение отдало заказ курьеру и больше за него не отвечает. В MVP закрывает
заказ джоба `courier` (§3.5) — тем же доменным переходом, с `actor = system`, по
таймеру `ORDER_DELIVERY_DURATION`: курьерской логистики нет, а статус обязан
доходить до конца. Точка расширения — §11.

### 4.2 CJM клиента (`docs/cjm-customer.puml`)

1. **Поиск** — фильтр по кухне, поиск по названию, только открытые, сортировка.
2. **Выбор** — меню по категориям; недоступные позиции **показываются** с
   пометкой, а не скрываются.
3. **Корзина** — одна на пользователя; блюдо из другого заведения → `409`.
4. **Проблемы, которые обязаны отработать:**
   - позиция кончилась, пока выбирал → `POST /cart/validate` вернёт дифф;
   - цена изменилась → пересчёт с явным подтверждением;
   - заведение закрылось → заказ не создаётся;
   - сумма ниже минимальной → `422` с указанием, сколько добрать.
5. **Оформление** — `Idempotency-Key` + `expected_total`.
6. **Отслеживание** — SSE; отмена только до `COOKING`.

### 4.3 CJM заведения (`docs/cjm-venue.puml`)

1. Старт сервиса, аутентификация по API-ключу, синхронизация меню.
2. Открытие смены → заведение появляется в выдаче.
3. Заказ приходит из Kafka → своя БД, позиции списываются с остатков.
4. Принять / отклонить с причиной → REST.
5. `COOKING → READY → HANDOVER`; блюдо кончилось → стоп-лист.
6. Закрытие смены.

Демо-заведение проходит этот путь само: `venue-service` — headless-сервис,
у него нет ни экрана, ни входящих ручек, а шаги 3–5 делает автопилот по
таймерам. Настоящий партнёр на этом же месте держит кассу с интерфейсом.

## 5. Схема БД

### `kitchen`

- `venues` — name, slug, description, address, lat/lon, is_active,
  is_open, min_order_amount, delivery_fee, avg_cook_minutes
- `cuisines` — slug (`italian`), name (`Итальянская`), position — справочник
- `venue_cuisines` — `PRIMARY KEY (venue_id, cuisine_id)` — связь M:N.
  Нормализовано осознанно: массив `text[]` нарушил бы 1НФ и не дал бы ссылочной
  целостности (опечатки и дубли значений), справочника для фильтров на фронте
  (`GET /cuisines`) и возможности навесить на кухню атрибуты
- `venue_api_keys` — venue_id, key_hash, revoked_at
- `menu_categories` — venue_id, external_id, name, position
- `menu_items` — venue_id, category_id, **external_id**, name, description,
  price, position, is_available, stock_qty (NULL = безлимит).
  `UNIQUE(venue_id, external_id)`. `position` — порядок показа внутри
  категории, как у `menu_categories`: карту составляет заведение, и алфавит
  её не восстанавливает
- `carts` / `cart_items` — `UNIQUE(user_id)`, `UNIQUE(cart_id, menu_item_id)`.
  В `cart_items` лежит `price_snapshot` — цена на момент добавления: без неё
  `POST /cart/validate` не с чем сравнивать текущую и `price_changed`
  необнаружим
- `orders` — number, user_id, venue_id, status, items_total, delivery_fee, total,
  address (nullable — задел под самовывоз), phone, comment, eta_minutes,
  rejection_reason, version. `UNIQUE(number)`.
  **`version` — не оптимистическая блокировка:** конкуренцию держит
  `SELECT ... FOR UPDATE`, а версия уезжает в поле `version` конверта события
  (§8) как версия агрегата
- `idempotency_keys` — `PRIMARY KEY (user_id, key)`, endpoint, request_hash,
  response_status, response_body jsonb, expires_at.
  **Отдельная инфраструктурная таблица, не колонка в `orders`:** ключ — свойство
  HTTP-запроса, а не заказа; он протухает через сутки, а заказ живёт вечно;
  механизм переиспользуется для любой ручки (`endpoint` разводит их), а не только
  для создания заказа. Чистится по `expires_at` тем же воркером, что и outbox,
  не трогая `orders`. В `response_body` лежит реальный отданный ответ — ретрай
  получает его побайтово, а не пересобранный из изменившегося состояния.
  **`user_id` в первичном ключе — изоляция, не уникальность:** при `PK (key)`
  чужой (подсмотренный или совпавший) ключ вернул бы `response_body` другого
  пользователя с его адресом и телефоном. Проверку владельца можно написать
  руками, но её можно и забыть при рефакторинге; с парой в PK чужой ключ просто
  не находится и запрос идёт обычным путём
- `order_items` — **снапшот**: name_snapshot, price_snapshot, qty,
  `line_total bigint GENERATED ALWAYS AS (qty * price_snapshot) STORED`.
  Избыточно по нормализации, но заказ — финансовый документ: он должен читаться
  через годы, а не пересчитываться сегодняшними правилами. Генерируемая колонка
  исключает рассинхрон; при появлении скидок станет обычной
- `order_status_history` — from_status, to_status, actor (`customer`/`venue`/`system`),
  reason. Её `id` используется как `seq` в SSE
- `outbox_messages` — event_id, topic, key, event_type, aggregate_id,
  aggregate_version, payload jsonb, created_at, published_at, attempts,
  last_error. Поля конверта (§8) лежат колонками, а не собираются при
  публикации: **`event_id` обязан пережить ретрай**, иначе inbox-дедуп у
  потребителя не сработает. `created_at` он же `occurred_at` — строка
  пишется в одной транзакции с доменным изменением
- `processed_events` — event_id, consumer (inbox-дедуп)

Индексы: `orders(user_id, created_at DESC)`, `orders(venue_id, status)`,
`outbox_messages(id) WHERE published_at IS NULL` — по `id`, а не по
`created_at`, потому что джоба `outbox` забирает батч в порядке `id` (§3.5),
`venue_cuisines(cuisine_id, venue_id)`, GIN `venues(name gin_trgm_ops)` —
расширение `pg_trgm` делает `ILIKE '%q%'` индексируемым, иначе seq scan.

### `venue` — схема нашего демо-сервиса, а не требование к партнёрам

Реальный партнёр хранит данные как хочет (своя POS, 1С, что угодно) — мы требуем
от него только поведение из §7.4. Наш `venue-service` показывает один
правдоподобный способ реализации:

`dishes` (own sku, name, price, stock, is_available), `incoming_orders`
(main_order_id, payload, state, received_at, decided_at), `processed_events`.

ERD генерируется в `docs/erd.puml`.

## 6. Клиентский API (`api/openapi/kitchen.yaml`)

Префикс `/api/v1`, заголовок `X-User-Id`.

```
GET    /cuisines                  справочник для фильтров
GET    /venues?q=&cuisine=&open_now=&sort=&cursor=&limit=
GET    /venues/{venue_id}
GET    /venues/{venue_id}/menu

GET    /cart
PUT    /cart/items                { venue_id, item_id, qty }   qty=0 → удалить
DELETE /cart/items/{item_id}
DELETE /cart
POST   /cart/validate

POST   /orders                    Idempotency-Key: <uuid>
GET    /orders?status=&cursor=
GET    /orders/{id}
POST   /orders/{id}/cancel
GET    /orders/{id}/events        SSE
```

Ключевые детали:

- **Курсорная пагинация**, не offset — offset разъезжается при вставках.
- **`PUT /cart/items`** вместо POST: «сделать так, чтобы было N штук» —
  идемпотентно, безопасно ретраить.
- **`POST /cart/validate`** — центральная ручка CJM, возвращает список проблем:
  `price_changed`, `out_of_stock`, `item_unavailable`, `venue_closed`,
  `below_minimum`. Фронт обязан дёрнуть её перед экраном оформления.
- **`POST /orders`** принимает `expected_total`; расхождение с расчётом сервера →
  `409 price_mismatch`. Клиент не платит больше, чем видел на экране.
- Повтор с тем же `Idempotency-Key` → `200` и сохранённый ответ вместо `201`.
  Обрабатывается **в middleware**, в одной транзакции с юзкейсом:
  `INSERT INTO idempotency_keys ... ON CONFLICT DO NOTHING RETURNING key`;
  пусто → сверяем `request_hash` и отдаём `response_body` (или `422
  idempotency_key_reuse`); вставилось → выполняем юзкейс и дописываем ответ в ту
  же строку. Атомарно даже при одновременных ретраях —
  Postgres сериализует на первичном ключе.
- **Ключ идентифицирует намерение, а не содержимое.** Фронт генерирует новый
  UUID при открытии экрана оформления. Поэтому второй точно такой же заказ
  (та же корзина, тот же адрес) оформляется свободно — у него другой ключ.
  Дедупликация по содержимому этот сценарий сломала бы, поэтому её и нет.
- **`request_hash` — детерминированная сериализация распарсенной DTO**
  (отсортированные ключи), а не хеш сырого тела. Хеш байт ломал бы легитимный
  ретрай при другом порядке ключей в JSON или работе прокси, а ложный отказ в
  оформлении хуже той ошибки, которую хеш ловит. Считаем сами из провалидированной
  структуры → generic, кода на ручку ноль. Единственное требование: **не класть
  волатильные поля в DTO запроса** (`client_sent_at`, nonce). Задача хеша узкая —
  поймать баг клиента, забывшего обновить ключ для новой корзины, вместо
  молчаливой выдачи прошлого заказа.
- **Ключ нужен только там, где создаётся сущность.** Всё остальное идемпотентно
  по конструкции: `PUT /cart/items` — «пусть будет N штук»; партнёрские
  `accept`/`cooking`/`ready` и `POST /orders/{id}/cancel` — переходы в названное
  целевое состояние, повтор возвращает `200` и ничего не делает (это свойство
  FSM, а не отдельный механизм). Во всём MVP `Idempotency-Key` требуется на
  одной ручке — `POST /orders`. Механизм при этом общий: ручки помечаются в
  спеке `x-idempotent: true`, middleware читает это из embedded-spec, так что
  добавление второй — декларативное.
- Заказы привязаны к `orders.user_id` и видны с любого устройства. Откуда
  берётся `user_id` (JWT, сессия, шлюз) — за рамками MVP: считаем, что он пришёл
  честно.
- Меню отдаёт недоступные позиции с `is_available: false` и `unavailable_reason`.

Единый формат ошибок: `{ code, message, details, trace_id }`.
Несуществующий или чужой заказ → `404` (не `403`, чтобы не подтверждать
существование идентификатора).

## 7. Партнёрский API и интеграция

### 7.1 Главное решение: партнёр не предоставляет никакого API

Требовать от кафе публичный HTTPS-эндпоинт — значит требовать белый IP,
сертификат, дежурного админа и т.д. Вебхуки отсекли бы большую часть рынка.

Поэтому **оба канала инициируются партнёром наружу**: исходящее подключение к
Kafka (читает заказы) и исходящий HTTPS к нам (шлёт статусы). Работает из-за
любого NAT. Ни одного входящего порта.

**Входящих ручек у `venue-service` нет вовсе** — только `/healthz` для
compose. Экран повара ему не нужен: заказы он берёт из Kafka, решения принимает
автопилотом, а наружу ходит сам. Партнёр, которому нужен интерфейс, ставит его
поверх той же связки и площадке об этом не сообщает.

### 7.2 Партнёрский REST (`api/openapi/partner.yaml`, `X-Api-Key`)

```
GET    /api/v1/partner/me
POST   /api/v1/partner/menu                       полная синхронизация
PATCH  /api/v1/partner/menu/items/{external_id}   стоп-лист / цена / остаток
POST   /api/v1/partner/shift/open | /close
GET    /api/v1/partner/orders?status=&since=&cursor=
GET    /api/v1/partner/orders/{id}
POST   /api/v1/partner/orders/{id}/accept         { eta_minutes }
POST   /api/v1/partner/orders/{id}/reject         { reason }
POST   /api/v1/partner/orders/{id}/cooking
POST   /api/v1/partner/orders/{id}/ready
POST   /api/v1/partner/orders/{id}/handover
```

Все ручки статусов идемпотентны: повтор `accept` на уже принятом заказе → `200`,
не ошибка (ретрай после таймаута не должен ронять кассу). Невалидный переход →
`409` с текущим статусом.

### 7.3 `external_id` — ключевое поле интеграции

Идентификатор блюда **в системе партнёра**. Отвечает на вопрос задания «как
связать данные в вашей системе с данными заведений»:

- `UNIQUE(venue_id, external_id)` → повторная выгрузка меню это upsert, а не дубли;
- партнёру не нужно хранить наши UUID — он оперирует своими SKU;
- в событии заказа возвращаем `external_id` → касса сразу знает позицию своей
  номенклатуры без таблицы соответствий.

### 7.4 Контракт

**Партнёр обязан:**

1. читать свой топик Kafka;
2. дедуплицировать по `event_id` — мы даём **at-least-once**, дубли неизбежны;
3. слать статусы по REST;
4. синхронизировать меню и стоп-листы.

**Порядок показа партнёр сообщает порядком массивов** в выгрузке меню, а не
отдельным полем: массив упорядочен сам по себе, и явная `position` рядом с ним
была бы вторым источником истины, способным ему противоречить. Мы раскладываем
индекс в `menu_categories.position` и `menu_items.position` с зазором, так что
внутри БД порядок остаётся редактируемым, а порог интеграции не растёт (§7.5).

**Мы гарантируем:**

| Гарантия | Детали |
|---|---|
| Доставка заказа | at-least-once; касса лежала час — заказы дождутся в топике |
| Порядок | партиционирование по `venue_id` → события заведения строго по порядку |
| Идемпотентность наших ручек | повторный вызов безопасен |
| Валидация переходов | `409` с объяснением вместо порчи состояния |
| Автоотказ | не принят за 5 мин → `REJECTED`, клиенту возврат |

При онбординге партнёр получает: `venue_id`, `X-Api-Key`, Kafka bootstrap + SASL
+ топик + **фиксированный `group.id`** (чтобы при перезапуске кассы продолжить с
того же offset, а не перечитать заказы за месяц), OpenAPI-спеку и JSON-схемы
событий.

### 7.5 Уровни интеграции

Требовать Kafka-консьюмера от каждого кафе нереалистично. В README описываем:

| Уровень | Кому | Как получает заказы |
|---|---|---|
| **A. Kafka + REST** | сети со своей IT-командой | consumer group — **реализуем в MVP** |
| **B. Только REST** | без Kafka-экспертизы | long-polling `GET /partner/orders?status=new&since=` |
| **C. Веб-кабинет** | пекарня без IT | UI поверх того же партнёрского API |
| **D. Вебхуки** | кто просит push | `callback_url` + HMAC-подпись + backoff |

**У всех уровней один и тот же партнёрский REST для записи** — различается только
способ доставки заказа партнёру. Для уровня B серверной логики почти не нужно:
одна ручка с курсором по `created_at`.

## 8. События (`api/asyncapi/events.yaml`)

Конверт:

```json
{ "event_id": "01J8X...", "event_type": "order.created",
  "occurred_at": "2026-08-26T10:00:00Z", "aggregate_id": "8f3a...",
  "version": 1, "payload": {} }
```

| Топик | Key | События | Консьюмеры |
|---|---|---|---|
| `kitchen.orders.v1` | `venue_id` | `order.created`, `order.cancelled` | заведения (группа на заведение) |
| `kitchen.order-status.v1` | `order_id` | `order.status_changed` | SSE-хабы (группа на инстанс) |

`key = order_id` в статус-топике гарантирует, что статусы одного заказа не
переупорядочатся. Топик — **шов для будущих консьюмеров**: push-нотификации,
сервис курьеров, аналитика времени готовки, SLA-монитор. Каждый — своя consumer
group, ноль правок в коде оформления заказа.

## 9. Структура репозитория

```
cmd/                    бинари ПЛОЩАДКИ и только они
  kitchen-api/          HTTP API + SSE-консьюмер
  worker/               outbox + order-reaper + idempotency-gc
  seed/                 демо-заведения и API-ключи (идемпотентно)
  demo/                 сквозной сценарий против живого compose
internal/               код площадки
  api/{kitchen,partner}api/  КОДОГЕН по спекам: модели, сервер, клиент
  config/
  domain/order/         FSM, инварианты — чистый Go, юнит-тесты
  domain/cart/          пересчёт, валидация
  usecase/              usecase-слой
  repo/postgres/        pgx, транзакции, outbox
  transport/http/       хендлеры и middleware, маппинг кодогена в домен
  transport/sse/        хаб подписчиков
  broker/kafka/         producer, consumer, inbox
  platform/{logger,httpx}
venue/                  ДЕМО-СЕРВИС ЗАВЕДЕНИЯ целиком, отдельно от площадки
  cmd/venue-service/
  internal/             своя БД, консьюмер заказов, автопилот, клиент площадки
  migrations/           своя схема — её применяет он сам
api/openapi/{kitchen,partner}.yaml
api/asyncapi/events.yaml
migrations/kitchen/*.sql   схема ТОЛЬКО площадки
docs/*.puml
.golangci.yml  Makefile  docker-compose.yml  Dockerfile  README.md  PLAN.md
```

**Граница проведена каталогом.** В `cmd/` и `migrations/` нет ничего от
заведения: площадка не знает ни про его БД, ни про его бинарь. Обратно
`venue/` ходит только через сгенерированный из спеки клиент и Kafka —
ровно теми путями, что доступны настоящему партнёру.

**Кодоген лежит отдельно от транспорта.** `internal/api/*` — артефакт
контракта, а не слой площадки: из партнёрской спеки генерируется не только
сервер, но и клиент, которым ходят `venue/` и `cmd/demo`. Держать его внутри
`transport/http/` значило бы, что демо-заведение импортирует транспорт
площадки. Имя пакета включает область (`kitchenapi`, `partnerapi`), потому что
читается оно на дальнем call site, а не в своём каталоге.

Линтеры: `golangci-lint` (errcheck, govet, staticcheck, revive, gosec, errorlint,
bodyclose, sqlclosecheck, gocritic), `gofumpt`. CI: GitHub Actions — lint, test,
build, проверка актуальности кодогена.

### 9.1 Подготовка базы и старт приложений

«Схема применена» и «приложение работает» — разные события, поэтому и команды
разные. `migrator` и `seeder` — одноразовые сервисы под профилем `setup`:
`docker compose up` их не выбирает вовсе, приложения на них не ждут и в
`depends_on` не ссылаются.

```yaml
migrator:      image: migrate/migrate, profiles: [setup], restart: "no"
               depends_on: { postgres: { condition: service_healthy } }
seeder:        profiles: [setup], restart: "no"
               depends_on: { migrator: { condition: service_completed_successfully } }
kitchen-api:   ports: ["8081:8081"]
               depends_on:
                 postgres: { condition: service_healthy }
                 redpanda: { condition: service_healthy }
```

Порядок внутри профиля держит тот же `service_completed_successfully`:
`docker compose run` поднимает зависимости цели, так что `make seed` сам
проходит цепочку postgres → migrator → seeder. Профиль команде `run` указывать
не нужно, она включает его сама; а вот `down` и `ps` профильные сервисы
игнорируют — поэтому в Makefile они идут с `--profile "*"`, иначе остановленные
`migrator` и `seeder` остаются висеть.

Рабочая последовательность на чистой машине: `make up`, `make migrate-up`,
`make seed`.

**Healthcheck postgres ходит по TCP** (`pg_isready -h 127.0.0.1`). Официальный
образ перед настоящим сервером поднимает временный, только на unix-сокете
(`-c listen_addresses=''` в его `docker-entrypoint.sh`), чтобы прогнать
init-скрипты по ещё не готовой базе, никого к ней не пуская. Проверка по сокету
проходит на этом временном сервере — на замере окно между ним и TCP настоящего
длилось 2.7 с, — и `migrator` следом получает `connection refused`. Проверка по
сокету при большом `interval` может в это окно и не попасть, но зависеть тут от
совпадения интервала с длительностью initdb не хочется: `migrate` подключается
сразу и без ретраев.

Свою схему `venue-service` готовит сам, своим шагом: площадка про его базу
не знает и не создаёт её. Локально миграции гоняются тем же образом —
`make migrate-up` это `docker compose run --rm migrator`, — так что версия
инструмента одна и та же в compose, в CI и на машине разработчика.

### 9.2 Откуда берутся данные

Три источника, по природе данных:

| Данные | Где | Почему |
|---|---|---|
| Справочник `cuisines` | **миграция** | reference data, часть схемы, нужна и на проде |
| Заведения + API-ключи | **`cmd/seed`**, идемпотентно (`ON CONFLICT DO NOTHING`) | демо-данные в миграциях — антипаттерн. Смысл: площадка заранее знает список заведений, это «закрытый доступ» из задания |
| Меню демо-заведения | **сам `venue-service` через партнёрский API при старте** | `GET /partner/me` → `POST /partner/menu` → `POST /partner/shift/open`. Меню приезжает тем же путём, что у реального партнёра — первые три шага CJM заведения проверяются на каждом `up`, а не описаны на словах |

Меню двух остальных заведений (у них нет своего сервиса) — в seed: они изображают
партнёров, интегрировавшихся раньше, чтобы каталог не был пустым.

**API-ключ:** в БД лежит `sha256(key)`, сам ключ (`vk_demo_bakery_dev`) — в env
`venue-service`. SHA-256, а не bcrypt: bcrypt нужен для паролей с низкой
энтропией, а 256-битный случайный токен не перебирается, и медленный хеш лишь
добавил бы задержку к **каждому** партнёрскому запросу. Сравнение —
`subtle.ConstantTimeCompare`. Ручка генерации ключа для реального онбординга —
точка расширения, в MVP не делаем.

### 9.3 Тесты и моки

**Table-driven — стиль по умолчанию.** Проверяем не «работает ли функция», а
таблицу случаев: каждая строка — имя, вход, ожидание. Так добавление случая
стоит одну строку, а `go test -run` показывает, какой именно случай упал.
Отдельными функциями пишем только то, что в таблицу не ложится: сценарии с
шагами во времени (graceful shutdown, реплей SSE) и интеграционные прогоны.

Три уровня, каждый на своём материале:

| Уровень | Что покрывает | Чем |
|---|---|---|
| Юнит | FSM заказа, пересчёт корзины, чистые функции домена | таблицы, без моков вообще — домен ни от чего не зависит |
| Юзкейс | ветвления сценария: нет остатка, чужой заказ, закрытая смена | моки репозиториев, сгенерированные `mockery` |
| Интеграционный | сквозной путь заказа | testcontainers: настоящие Postgres и Redpanda |

**Моки генерируются, а не пишутся руками.** Рукописная заглушка молча
разъезжается с интерфейсом и переживает его переименование; сгенерированная
ломает сборку. Инструмент — `mockery`, объявленный tool-зависимостью в
`go.mod` (его документация рекомендует именно этот способ), вызов —
`go tool mockery`, цель — `make mocks`. Файлы `*_mock.go` руками не правим.

Интерфейс объявляет **потребитель**, рядом с юзкейсом, и он узкий — ровно те
методы, которые нужны этому сценарию. Поэтому в `.mockery.yml` перечислены
интерфейсы из `internal/usecase/*`, а не из `internal/repo`.

```yaml
all: false
dir: "{{.InterfaceDir}}/mocks"
pkgname: "mocks"
filename: "{{.InterfaceName | snakecase}}_mock.go"
force-file-write: true
structname: "{{.Mock}}{{.InterfaceName}}"
template: testify
packages:
  avito-kitchen/internal/usecase/catalog:
    interfaces:
      VenueRepository: {}
      MenuRepository: {}
  avito-kitchen/internal/usecase/order:
    interfaces:
      OrderRepository: {}
      MenuRepository: {}
      Outbox: {}
```

Список растёт по этапам вместе с юзкейсами; конфиг появляется на этапе 2 —
вместе с первым интерфейсом, до этого генерировать нечего.

## 11. Допущения (в README)

- Нет авторизации клиента — `X-User-Id` как заглушка (разрешено заданием).
  Считаем, что `user_id` пришёл честно; в реальной системе он приезжает из JWT
  или от шлюза. Заказы привязаны к нему в БД, поэтому подмена способа
  аутентификации не затрагивает ни схему, ни логику.
- Нет оплаты: заказ считается оплаченным при создании.
- Курьерская логистика заглушена: `DELIVERING → DELIVERED` ставит площадка
  джобой `courier` по таймеру, а не заведение — партнёрской ручки `deliver`
  нет (§4.1).
- Геопоиск упрощён до фильтра по тегам и городу, без гео-индекса.
- Меню без модификаторов и опций блюд.
- Нет rate-limiting, кэша, распределённого трейсинга; из наблюдаемости —
  структурные логи, `trace_id` и `/healthz`.
- Одна БД без read-реплик. При их появлении состояние заказа для SSE-снапшота
  обязано читаться с primary — иначе лаг репликации даст пропущенный статус.
- Один инстанс `kitchen-api` без балансировщика: горизонтальное масштабирование
  не входит в задание. Код к нему готов — хаб SSE не держит общего состояния, а
  статусы ходят через Kafka, а не через память процесса (§3.3).

**Спроектированные точки расширения:**

- **Самовывоз.** `fulfillment_type` (`DELIVERY`/`PICKUP`) на заказе; ветка
  `READY --pickup--> PICKED_UP`, `delivery_fee = 0`, `address` не требуется.
  Стоит две строки в таблице переходов и одну миграцию — потому что FSM
  задан данными, а `address` уже nullable (§4.1).
- **Новые потребители статусов** — push/SMS, поиск курьера при `READY`,
  аналитика времени готовки, SLA-монитор. Каждый — своя consumer group на
  `kitchen.order-status.v1`, ноль правок в коде оформления заказа. Ради этого
  шва топик и существует.
- **Курьерский сервис.** Сегодня `DELIVERING → DELIVERED` закрывает заглушка
  площадки; в настоящей системе «доставил» жмёт курьер в своём приложении. Это
  отдельный сервис, а не правки заказа: `deliver` уже отдельное событие FSM и
  применяется тем же кодом, что и остальные переходы, а событие `READY` в
  `kitchen.order-status.v1` — готовый шов, чтобы такой сервис искал курьера. Из
  правок — `courier` в enum `order_actor` (одна миграция) и `courier_id` на
  заказе.
- **Второй экземпляр `worker`.** Джобы уже берут строки `FOR UPDATE SKIP
  LOCKED`, так что параллельные экземпляры не мешают друг другу и лидер им не
  нужен: `order-reaper` и `idempotency-gc` масштабируются репликой как есть.
  Мешает только порядок публикации в джобе `outbox` (§3.5) — два события одного
  заказа могут попасть в батчи разных воркеров. Лечится шардированием выборки:
  `WHERE hashtext(aggregate_id::text) % $N = $I`, где `N` — число реплик, `I` —
  индекс экземпляра из окружения. Все события одного заказа всегда достаются
  одному воркеру, а `SKIP LOCKED` продолжает страховать от зависших локов.
  Ценой этого гарантия сужается с «заказы одного заведения не
  переупорядочиваются» до «события одного заказа не переупорядочиваются» — то
  есть ровно до того, что партнёру и нужно (§7.4).
- **Уровни интеграции B/C/D** для партнёров без Kafka (§7.5).

**Масштабирование:** горячая партиция у крупной сети лечится более гранулярным
ключом (`venue_id:point_id`); вынос каталога и поиска в отдельный сервис с
полнотекстовым индексом или Elasticsearch; замена outbox-воркера на CDC
(Debezium); шардирование `orders` по `user_id`; шардирование SSE-консьюмеров
вместо полного broadcast.

## 12. Верификация

1. `docker compose up --build` — по цепочке §9.1 отрабатывают `migrate` и `seed`,
   затем поднимаются redpanda, redpanda-console (:8080), kitchen-api (:8081),
   worker и venue-service (:8082). Последний сам выгружает меню через
   партнёрский API и открывает смену.
2. **`make demo` → `go run ./cmd/demo`** — Go-программа, а не bash-скрипт:
   работает одинаково на Windows/Mac/Linux, не требует curl и jq, ждёт события
   каналом с таймаутом вместо `sleep`, и — главное — ходит через
   **сгенерированный из спеки клиент**, так что расхождение спеки с реализацией
   ломает сборку демо.
   Сценарий: список заведений → меню → корзина → `validate` → заказ → SSE-поток в
   горутине → автопилот заведения принимает и готовит. Проверяется **вся
   последовательность** `ACCEPTED → COOKING → READY → DELIVERING → DELIVERED`, а
   не только финальный статус.
3. Негативные проверки в том же `cmd/demo`:
   - повтор `POST /orders` с тем же `Idempotency-Key` → тот же заказ;
   - тот же ключ с изменённой корзиной → `422 idempotency_key_reuse`;
   - заказ на позицию с `stock_qty = 0` → `409`;
   - отмена из `COOKING` → `409`;
   - изменение цены между `validate` и `POST /orders` → `409 price_mismatch`;
   - `docker compose stop venue-service` → создать заказ → `start` → заказ
     доезжает из Kafka;
   - заказ без `accept` дольше `ORDER_ACCEPT_TIMEOUT` (в демо 30 с) →
     авто-`REJECTED` от `order-reaper` с возвратом остатков.
4. `make test` (юниты + testcontainers), `make lint`,
   `make generate && git diff --exit-code` — кодоген актуален.
5. Топики, лаг консьюмеров и содержимое сообщений — в Redpanda Console на :8080.
6. `make diagrams` рендерит `docs/*.puml`.
